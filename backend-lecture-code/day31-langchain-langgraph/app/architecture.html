🍕 Slice Pizza: how the chatbot works

A plain chat window talks to an Express server. The server runs one LangGraph graph for every message. LangGraph draws the boxes and arrows, keeps the shared state, saves a checkpoint after every box and pauses for a human. LangChain supplies what runs inside each box: the model, structured output, the retriever, createAgent and the tools. All the agent logic is in the backend.

1. The big picture

Four moving parts. The browser only knows three routes and five event types; it has no idea a graph exists.

2. One message, start to finish

The customer types "two large pepperonis and a coke". Read the arrows top to bottom.

  1. The browser sends the message with its thread id. The response stays open: it is a stream, not one JSON reply.
  2. The server hands the message to the graph under that thread id.
  3. The checkpointer loads everything saved for that thread: earlier messages and the cart.
  4. classify asks the model for a structured answer: one of four intents. The model only labels the message.
  5. The intent is written to the state. A conditional edge reads it, and our code picks the path (here orderAgent).
  6. The agent loop: the model asks for tools, LangChain runs them on the cart, the model reads the results, and so on until it has nothing left to ask for (capped at six model calls).
  7. The final reply text is added to the state as a new message.
  8. After every node, LangGraph saves a checkpoint. That one habit makes pausing and restarting possible.
  9. While the graph runs, it streams events back to the server: "a node finished" and "the model wrote some text".
  10. The server forwards them as node and token events. Tokens come only from the nodes the customer reads, not from classify.
  11. When the stream ends, the server reads the saved end state and sends one closing done event with the cart, the total and the final reply.

3. The graph

The whole graph is a workflow: the paths are fixed by us. Only one box, orderAgent, is an agent, because cart edits are open-ended and need a variable number of steps.

4. Checkout: pause, then resume

The part that is hardest to picture. The graph stops in the middle of a node and continues later, even after a server restart.

  1. The customer says "check out". The browser sends it like any other message.
  2. The server starts the graph.
  3. classify labels the message checkout. The cart is not empty, so the route goes to confirm.
  4. confirm calls interrupt(). The node stops there, and nothing below that line runs.
  5. LangGraph saves a checkpoint that says "paused inside confirm", together with the question and the cart.
  6. The stream ends. The graph is not running any more; it is just a saved row.
  7. The server sees the pause and sends an interrupt event instead of done.
  8. The browser shows the Confirm card and disables the text box. New messages are refused (HTTP 409) until the card is answered.
  9. The customer clicks Confirm. The browser calls POST /api/chat/resume with { approved: true }.
  10. The server resumes the same thread with Command({ resume: true }), the answer to the question interrupt() asked.
  11. The checkpointer loads the paused state. This could be a different server process from the one that paused it.
  12. confirm runs again from its first line. This time interrupt() returns the customer's answer instead of stopping.
  13. The edge after confirm sees confirmed = true and runs placeOrder, which charges the card and creates the order id.
  14. Events stream back as in a normal run.
  15. The browser gets done with the confirmation, and the cart is now empty.
Why the charge is in placeOrder, not in confirm: a resumed node re-runs from its first line, so anything with a side effect placed above the interrupt() would happen twice (and would happen even if the customer said no).

5. State: what the graph remembers

Every node reads one shared object and returns only the keys it changes. This is the PizzaState in graph.ts.

KeyHow a new value is mergedWho reads and writes it
messagesAppended: new messages are added to the list, never replace itclassify reads. answer, orderAgent, placeOrder, cancel and orderStatus each add one reply.
intentLast write winsclassify writes it. The routing function reads it.
cartLast write wins: a node returns the whole new cartorderAgent writes it (through its tools). placeOrder empties it. answer and confirm read it.
confirmedLast write winsconfirm writes the customer's answer. The next edge reads it.

6. How the app behaves

  • One chat = one thread id. Messages, the cart and any open approval are saved under it. "New chat" makes a new, empty thread.
  • The model labels, our code routes. A wrong label means a wrong path, which is why classify's prompt describes each intent.
  • Questions are answered from the documents. answer uses only the retrieved chunks, the price list and the cart, and says it is not sure if they do not cover the question.
  • The agent edits the cart only through three tools (add, remove, view). Prices and totals are worked out in code (shop.ts), never by the model, and the loop is capped at six model calls.
  • Replies stream as they are written. Text written before a tool call ("Let me add that…") is cleared when the tools run, and the final reply replaces the bubble.
  • Checkout always asks first. Nothing is charged until the customer confirms. Cancel keeps the cart. Checking out an empty cart is routed to answer, so it never reaches the payment steps.
  • Reload or restart is safe. GET /api/chat/:threadId rebuilds the chat, the cart and any open Confirm card from the saved checkpoint.
  • Errors are shown, not swallowed. A failed run sends an error event and the bubble says "Something went wrong".

7. Known limits (on purpose, for a demo)

  • Placed orders and their numbers (S-1004, …) live in server memory (shop.ts), not in SQLite. After a restart the app forgets them and numbering starts again.
  • The vector store is rebuilt from the three documents at every start. A real app would use a persistent vector database.
  • The path label under each reply is not saved, so replies loaded after a reload show without it.
  • No login (any thread id works) and no real payment provider: "charging the card" is a log line.

Where each idea lives in the code

  • Workflow / routing: routeByIntent and the addConditionalEdges calls in backend/src/graph.ts. The model classifies, our code picks the path.
  • Structured output: classify returns a typed { intent }, from a zod schema.
  • RAG: answer (retrieve, then generate) and backend/src/knowledge.ts (load, split, embed, store).
  • Agent loop and tool calling: orderAgent and cartTools. createAgent runs the loop for us.
  • Guardrails: modelCallLimitMiddleware (cap on the loop) and the empty-cart check in routeByIntent.
  • Human in the loop: confirm calls interrupt(). The charge lives in placeOrder, after the approval, because a resumed node re-runs from its first line.
  • State and persistence: PizzaState and the SQLite checkpointer. GET /api/chat/:threadId rebuilds the chat, the cart and any open approval from it.
  • Streaming: runGraph in backend/src/server.ts turns the graph's stream into Server-Sent Events (node, token, done or interrupt).
