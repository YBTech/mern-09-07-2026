# Day 23: Monitoring & Observability, lecture code

An e-commerce backend (a gateway and five microservices) that sends **metrics, logs and traces** to
Grafana's LGTM stack through OpenTelemetry. k6 plays the customers, from a gentle trickle up to a
stress test that pushes the shop until something breaks, so you can *see the bottleneck* in the
dashboards instead of guessing.

It also contains one deliberate production bug, and three before/after performance pairs.

```
k6 (fake customers) ─► gateway :4000 ─┬─► catalog       :4001   products, prices, promo, recommendations
                                       ├─► orders        :4002   checkout; calls catalog, inventory, payments, notifications
                                       │      ├─► catalog        price of each item
                                       │      ├─► inventory :4003    reserve stock (row lock per product)
                                       │      ├─► payments  :4004    charge the card (external provider, limited slots)
                                       │      └─► notifications :4005  confirmation email (not awaited)
                                       └─► (inventory, orders also called directly by /api/dashboard/*)

every service ── OTLP ─► otel-lgtm container: Collector → Loki (logs) · Prometheus (metrics) · Tempo (traces) → Grafana :3000
```

Data lives in memory. `services/shared/fakeDb.ts` is a pretend Postgres: each query takes a realistic
round trip, appears as a DB span in traces, and **borrows a connection from a fixed-size pool**
(that pool is a bottleneck you'll find). Nothing to install besides Docker and Node.

## Setup

```bash
docker compose up -d     # the LGTM stack. First start ~30s; Grafana is ready at http://localhost:3000
npm run setup            # npm install
npm run dev              # all six services in one terminal
```

| Open                                 | What                                              |
| ------------------------------------ | ------------------------------------------------- |
| http://localhost:3000                | Grafana → Dashboards → **Day 23** → three dashboards (below) |
| http://localhost:3000/explore        | Explore: query Tempo (traces) / Loki (logs) / Prometheus (metrics) directly |
| `requests.http`                      | Click-to-run requests for every demo (IntelliJ / VS Code REST Client) |

```bash
npm run load:shop        # ~4 min of comfortable, realistic traffic (includes the bug)
npm run load:compare     # 2 min hitting each before/after pair equally
npm run load:stress      # ~9 min, ramping until the shop breaks
docker compose down      # stop the stack (telemetry is not kept)
```

Only warnings and errors print in the `npm run dev` terminal (so a load test doesn't scroll away). Loki
still gets every line. Set `LOG_STDOUT_LEVEL=info` to see everything.

**Resource limits** (`docker-compose.yml`): LGTM is capped at 2 CPUs / 2.5 GB, k6 at 2 CPUs / 1 GB. Each Node
service is single-threaded, so none can use more than one core. Everything runs on your machine, so
close heavy apps before the stress test: a starved laptop would be a bottleneck of its own.

## The three dashboards

Generated by `grafana/build-dashboards.py` (`npm run dashboards` after editing it: don't edit in the
Grafana UI, it isn't saved to disk). Each answers one question.

| Dashboard | Question | Panels |
| --------- | -------- | ------ |
| **1 · Overview** | *Is the shop healthy? Which service is slow? What failed?* | The four golden signals at the gateway · **p50 / p95 / p99 response time of every service** · a sortable table of every endpoint (req/s, p50, p95, p99, error %) · traffic and errors per service · unhandled exceptions by type · service map (from traces) · time spent calling each dependency · error traces + error logs · the before/after pairs |
| **2 · Bottlenecks** | *What is running out of capacity?* | Throughput vs. p95 (find the ceiling) · where the time goes, by kind of span · **the queues**: DB pool, inventory row lock, payment provider slots · **the processes**: CPU, event-loop utilization and delay, memory, GC |
| **3 · Business** | *What does this cost the shop?* | Orders and revenue per minute · orders refused (declined / out of stock) vs. crashed · **revenue lost to the bug** · payments by outcome · stock per product · emails sent |

## Demo 1: the three signals (10 min)

1. `npm run load:shop`. Open dashboard **1 · Overview**. The top row is the **four golden signals**
   (traffic, errors, latency; saturation is dashboard 2).
2. **Metrics:** the errors panel shows `POST /orders` failing about 1 in 10 times, above the 1% line. *Is*
   something wrong? Yes. *Where*, and *why*? Metrics can't say.
3. **Traces:** Explore → Tempo → Search → service `gateway`. Open any `POST /api/orders` trace: **one request
   crossing five services**: gateway → orders → catalog (price) → inventory (reserve, with a row-lock
   wait span) → payments (a queue span, then the provider call) → INSERT, and notifications *after*
   the response (fire and forget).
4. **Logs:** Explore → Loki → `{service_name="orders"}`. Expand a line: `trace_id` is there, added
   automatically. In Tempo, a span's **Logs for this span** button jumps straight to them.
5. **Service map:** Overview → *Service map*. Same data as traces, drawn as boxes and arrows.

## Demo 2: debug the production bug (15 min)

Run `npm run load:shop` if it isn't running. Pretend you're on call and the error alert just fired.

1. **Metrics, *when* and *how bad*:** Overview → errors panel. Only `POST /orders` fails, about 1 in 10.
   Dashboard **3 · Business** says what it costs: *Checkouts lost to crashes* and the estimated
   *revenue lost to crashes per minute*. A "small" bug has a price tag.
2. **Traces, *where*:** Overview → *Traces with errors*. Open one. The red span is in **orders**. Its
   exception event says `TypeError: Cannot read properties of undefined (reading 'percent')` and the stack
   trace points at `services/orders/pricing.ts`. Note what's *not* red: catalog, inventory and payments
   are fine. The Overview's *Unhandled exceptions by type* panel agrees: a `TypeError` is a code bug,
   not a bad request.
3. **Logs, *what exactly*:** *Error logs* panel, expand a line. The `body` field shows the order that
   failed. Compare a few: every failure has **quantity ≥ 5**, and only for certain products.
   (LogQL: `{service_name="orders"} | severity_text="error"`.)
4. **Reproduce locally:** `requests.http` has both requests, or:
   ```bash
   # 5 × Monitor stand (p3): HTTP 500
   curl -X POST localhost:4000/api/orders -H 'content-type: application/json' \
     -d '{"items":[{"productId":"p3","quantity":5}]}'
   # 5 × Mechanical keyboard (p1): works
   curl -X POST localhost:4000/api/orders -H 'content-type: application/json' \
     -d '{"items":[{"productId":"p1","quantity":5}]}'
   ```
5. **Root cause:** ask the class to read `pricing.ts`, `catalogClient.ts`, and `catalog/products.ts`.

   <details><summary>Answer</summary>

   Catalog's `bulkDiscount` is **optional**: only some products have one. But Orders' own type
   for a catalog product (`catalogClient.ts`) declares it **required**, so TypeScript never
   warned that `product.bulkDiscount.percent` can crash. The type lied about the data. This is a
   classic contract mismatch between two services.

   Fix, in two places:
   ```ts
   // catalogClient.ts: tell the truth about the data
   bulkDiscount?: { minQuantity: number; percent: number };

   // pricing.ts: now TypeScript forces you to handle the missing case
   if (product.bulkDiscount && quantity >= BULK_QUANTITY) {
   ```
   </details>

6. **Test first:** add the regression test to `services/orders/pricing.test.ts` and watch it fail
   with the *exact* production error before you fix the code:
   ```ts
   it("charges full price for 5+ of a product with no bulk discount", () => {
     const stand = { id: "p3", name: "Monitor stand", priceCents: 3500 };
     expect(lineTotalCents(stand, 5)).toBe(17500);
   });
   ```
   `npm test` → red. Apply the fix → green.
7. **Ship and verify:** save. `tsx watch` restarts orders in about 1 second. Within ~30 seconds the error
   panel drops to 0, and *Checkouts lost to crashes* on the Business dashboard goes to zero. That is
   the "verify in monitoring" step.

To reset for the next class: `git checkout services/orders`.

## Demo 3: backend performance, before vs. after (10 min)

`npm run load:compare`, then look at the bottom of dashboard **1 · Overview**. When k6 finishes, it also
prints p95 per endpoint. The `before` thresholds fail and the `after` ones pass.

| Pair                                   | Typical p95        | Open a trace in Tempo and you'll see                      |
| -------------------------------------- | ------------------ | --------------------------------------------------------- |
| N+1 queries → one batched query        | ~300ms → ~40ms     | a staircase of 20 `SELECT order_items` spans → just 2     |
| no cache → cache-aside                 | ~300ms → ~2ms      | a 300ms `ml-service.recommend` span every time → nothing (served from memory) |
| sequential → `Promise.all`             | ~450ms → ~180ms    | three calls one after another → three side by side        |

Live-edit option: change a `BEFORE` handler to the `AFTER` approach while `load:compare` runs,
and watch its line drop on *p95 latency over time*.

## Demo 4: stress test, find the bottleneck (20 min)

Demo 3 compares two implementations when the shop is quiet. This one asks a different question: **how
much load can the shop take, and what gives first?**

1. Open dashboard **2 · Bottlenecks**, set the time range to *Last 15 minutes*, and run `npm run load:stress`
   (about 9 minutes; `STEP=20s npm run load:stress` is a 3-minute dry run).
2. Watch. The load steps up every minute. Narrate what each row shows and ask the class to **predict
   what gives first**. Roughly (your numbers will differ):

   | When | What you see | Where to look |
   | ---- | ------------ | ------------- |
   | min 0–2 | Everything flat and green. This is the baseline | all rows |
   | min 3 | **The best-seller's row lock queues.** Orders for `p1` wait for each other; other products don't | *Inventory row-lock wait, per product* (only p1 climbs). In a trace: a long `inventory.row-lock (waiting)` span |
   | min 4 | The admin report starts. **Orders' event loop stalls**: delay p99 jumps to ~100ms+ while no downstream is slower | *Event loop delay*; in a trace, a gap with nothing running |
   | min 5–7 | **Catalog's DB pool fills** (6/6 connections) and a queue forms. Browse latency climbs, and so does checkout, because it asks catalog for prices | *DB connections in use vs. pool size*, *Queries waiting*; in a trace, a `db.pool.acquire (waiting…)` span: the *query* is fast, getting a connection isn't |
   | min 7+ | Requests start hitting the gateway's 3s timeout: **504s**. The breaking point | Overview → errors; k6's summary |

3. **Read the ceiling.** *Checkout: orders per second vs. p95 latency*: throughput flattens while latency
   keeps climbing. Latency didn't rise because anything got *slower*. Work started **waiting in line**.
   *Where does the time go* confirms it: the growing bands are `waiting` spans, not query or provider spans.
4. **Fix the first bottleneck, then find the next.** The lock is held 100ms per reservation. Pretend we
   made the update cheaper:
   ```bash
   LOCK_HOLD_MS=10 npm run dev     # restart the services, then run the stress test again
   ```
   The p1 queue disappears. The next limit shows itself: **payments in flight reaches its limit** and a queue
   forms (*Payment provider slots*), while the provider's own latency stays ~250ms. We aren't waiting on
   a slow provider; we're waiting for a *slot*. (`PAYMENT_CONCURRENCY=20` moves that ceiling too.)
   Each fix reveals the next bottleneck: that is what performance work looks like.
5. **Same exercise, other knobs:** `DB_POOL_SIZE=20 npm run dev` moves catalog's ceiling. And that is
   *why* a bigger pool isn't free: the database behind it has to cope with all those connections.

**Teaching points:** saturation has a *queue length* you can chart before anything fails · p95 degrades
long before the average moves · the slow thing is rarely the thing that's busy · always change one
thing, then measure again.

## Troubleshooting

- **Dashboard empty:** metrics are pushed every 5s and graphs use 30s windows, so give it ~30s after
  traffic starts. Check that `npm run dev` shows all six services starting.
- **Port already in use:** something else is on 3000, 4000–4005 or 4318. Stop it, or move the services:
  `PORT_BASE=4100 npm run dev` (services use 4100–4105; point k6 at it with `BASE_URL=http://localhost:4100`
  when running k6 directly).
- **k6 can't reach the gateway:** the k6 container targets `host.docker.internal:4000`, so `npm run dev`
  must be running on the host.
- **Changed a dashboard in Grafana's UI?** It's not saved to disk. Edit `grafana/build-dashboards.py` and
  run `npm run dashboards`.
- **An old `day23-lgtm` container is still running** from before this folder was restructured?
  `docker compose down` from the old location (or `docker rm -f day23-lgtm`), then `docker compose up -d` here.
